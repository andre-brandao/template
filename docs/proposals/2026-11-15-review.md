# Review decisions and proposals (2026-11-15)

The 2026-11-15 polish pass audited six areas: shell, slices, agent, ui, backend and visual.
The fixes that needed no decision are in PRs #48 (ui), #49 (shell) and #50 (backend). This
document lists what is left: choices that need an owner's call, plus open product questions.

The raw audits and screenshots were local working files and are not committed. Tags like
"ui #12" or "backend 28" refer to finding numbers in those files. Each entry below repeats
the context it needs, so you don't need the audits to read it.

**Effort:** S is half a day or less, M is 1–2 days, L is 3 days or more. **+mig** means the
change needs a schema migration, so you run `db:generate` yourself. **+gen** means you run
`gen:spec` and `gen`.

## Already decided in this pass

These came up as proposals in the audits and were settled while the fixes were made. They
are listed here so nobody reopens them by accident.

- **`Inline` keeps its partly optimistic display** (slices B, ui #1). While a save runs, the
  control shows the typed value with a `Status` dot. If the save fails, the value reverts
  and the dot shows the failure. The cache is never written ahead of the server. PR #48
  fixed the failure path. S3 writes this down as a rule.
- **There is a shared row in ui** (slices A, visual B). `List.Root` and `List.Row` landed in
  PR #48. The slices still need to adopt them (see Follow-ups).
- **Dev tools sit bottom-right** (visual F, option 1). PR #49 put the TanStack devtools,
  shown on hover, and the Svelte inspector in the bottom-right corner.
- **No `ConfirmButton`** (ui G). Most destructive actions are `Menu.Item`s. U4 covers the
  shared confirm.

## Shell and navigation

### S1. Global ⌘K command palette

**Context.** ui exports a `Command` palette with a story, but no screen mounts it. Pages
have their own `C` (create) and `/` (search) hotkeys, but there is no global way to jump
between pages. The nav config already lists every destination with an icon. Three audits
(shell A, ui C, visual D) made this proposal separately.

**Options.**

1. **A palette built only from nav, mounted in Shell.** It reads commands from `page.data.nav`
   plus a short "Go to" list. The root layout passes slice actions (theme, open assistant,
   send feedback) as an `extra` prop. This is the same snippet and prop composition the
   agent dock uses. It adds no new API.
2. **Option 1 plus search.** A "Projects" group comes from `getProjectsOptions()`, and the
   query only runs while the palette is open. Todo search comes later.
3. **Each page registers its own commands** through a context store. This is a registry,
   which the minimal-design rule argues against. It is also context plumbing.

**Recommendation.** Do 1 now, and add 2 once 1 has been used for a while. Skip 3: page
hotkeys go in a `?` shortcut sheet instead. Add a `Search ⌘K` button to the Topbar, and
give `Action` optional `icon` and `keys` fields so rows can show a `Kbd`.

**Sketch.** One new file, `lib/components/layout/Palette.svelte`, and two optional fields on
ui `Action`.

```svelte
<script lang="ts">
	import { goto } from '$app/navigation';
	import { page } from '$app/state';
	import { createHotkey } from '@tanstack/svelte-hotkeys';
	import { Command, type Action } from '@template/ui';

	let { extra = [] }: { extra?: Action[] } = $props();
	let open = $state(false);
	createHotkey('Mod+K', () => (open = !open));

	const go = (group: string, label: string, href: string) => ({ group, label, hint: href, run: () => goto(href) });
	const commands = $derived([
		...[...page.data.nav.sections.top, ...(page.data.nav.sections.bottom ?? [])]
			.flatMap((s) => s.items)
			.map((i) => go('This section', i.label, i.href)),
		go('Go to', 'Projects', '/projects'),
		go('Go to', 'Todos', '/todos'),
		go('Go to', 'Settings', '/settings/account'),
		...extra
	]);
</script>

<Command bind:open {commands} />
```

Admin and Dev entries are shown only when `me.can(...)` allows them or `dev` is set.
Effort: M.

### S2. Where theme switching lives

**Context.** PR #49 moved `ThemeToggle` into `features/settings`. It now reaches the account
menu through an `account` snippet and saves through prefs. PR #48 made its options
`menuitemradio`, so arrow keys reach them. The same choice also appears on Settings →
Experience.

**Options.**

1. Keep it in the account menu. It works and is accessible now.
2. Remove it from the menu and offer it as palette commands ("Theme: Dark") and on
   Settings → Experience.

**Recommendation.** Do 2 once S1 ships. That removes the `account` snippet's only
use and leaves one place that switches the theme (`swap()` in `features/settings/theme.ts`).
Until S1 ships, keep 1. Effort: S.

### S3. When a control may show a value before it saves

**Context.** The house rule bans optimistic cache updates. Two places show a user's choice
before the server confirms it: `Inline`, which you approved, and the theme repaint. PR #49
gave the Experience page the same pattern: it reverts if the save fails and shows a
`Status` dot. Without a written rule, every new screen reopens the question.

**Options.**

1. A strict rule: wait for the save before showing the change, including for the theme.
2. One written exception that covers both cases.

**Recommendation.** Do 2. Add this to the root CLAUDE.md, under the no-optimistic rule:

> A control may show the value the user just entered while its save runs. It shows a
> `Status` dot, reverts if the save fails, and never writes the query cache ahead of the
> server. Lists, counts and other views still wait for the server.

Locale, formats and time zone follow the same rule. Effort: S (docs only).

1. Keep it.
2. Delete it. The SHA moves to `/dev` and to the foot of the account menu. The rail strip,

**Recommendation.** Do 2. Pages get denser, and one component and the `--footer` coupling

### S5. Signed-out `/` and where home lives

**Context.** A signed-out visitor at `/` sees `Hero`, a marketing-style page with its own
`Topbar`. The signed-in `/` is the only signed-in page without the sidebar. Its tiles repeat
the four `(home)` nav items, and the nav has no Home entry. Settings, Developers, Admin,
Dev and `u/[id]` all use `fallback: "/todos"`.

**Options.**

1. Keep both as they are.
2. Send signed-out visitors at `/` to `/login`, since `Frame` already shows the pitch. Move
   the signed-in home into `(app)/(home)/+page.svelte`, with a `Header.Root` and the
   widgets (Glance, Recent), and drop the tiles.
3. Do only the redirect and keep home outside the shell.

**Recommendation.** Do 2. It deletes `Hero.svelte`, the `Topbar` used outside the shell,
the signed-out branch in `Me` and the `main.home` CSS fork. The app isn't in production
yet, so it needs no compatibility redirect.

**Sketch.** Add `{ href: "/", label: "Home", icon: House, exact: true }` to the `(home)` nav,
change every `fallback: "/todos"` to `"/"`, and have `routes/+page.server.ts` redirect to
`/login` when there is no user (`next.gate` from PR #49 already does the check). Effort: M.

**Recommendation.** Do 1, and move it only when a second app needs it. Effort: none.

## UI system (`@template/ui`)

### U1. Where token defaults live

**Context.** ui components read tokens such as `--border`, `--ink` and `--control`, and
every use repeats a fallback. That is about 300 literals. PR #48 made every token use the
same fallback value, but nothing stops them from drifting apart again.

**Options.**

1. Keep fallbacks at each use. They are consistent today and need watching.
2. Add one `packages/ui/src/lib/tokens.css`, imported by `index.ts` and wrapped in
   `@layer ui.tokens { :where(:root) { … } }`. Components then use bare `var(--x)`. The
   app's `:root` overrides these defaults because `:where()` has zero specificity. The
   token list moves out of `routes/layout.css`, so the app only sets theme values.
3. Generate the fallbacks at build time from a TS token map. This adds tooling.

**Recommendation.** Do 2. There is one source of truth, components still read their tokens
themselves, and `sideEffects: ["**/*.css"]` already allows the import. Change the ui rule
from "every token written with a fallback" to "every token has a default in `tokens.css`".
Effort: M, mostly mechanical replacements.

### U2. Async and error states

**Context.** There are 13 copies of `isPending / isError / empty / else` chains and 12 bare
`<Issue>` error states. None of them can retry. `Issue` adds its own outer margin.
`FormBoundary` prints a fixed "Something went wrong." There are 18 `<svelte:boundary>`s with
no `failed` state, so one failing `getStats()` takes the whole admin page to the error page.

**Options.**

1. Keep the chains and add `Issue retry`.
2. Add a structural `<Query of={q}>` to ui with `pending`, `failed`, `empty` and
   `children(data)` snippets. It takes `{ isPending, isError, error, data, refetch }`, so it
   doesn't import TanStack.
3. Do 1 now, and rename `FormBoundary` to a general `Boundary` for remote queries.

**Recommendation.** Do 3 now and 2 later. The chains are short and explicit. Reconsider
once the todos rewrite lands and the number of chains is known.

```svelte
<Issue retry={list.refetch}>{list.error.message}</Issue>
<Boundary>{#snippet pending()}<Skeleton …/>{/snippet} …</Boundary>  <!-- failed → <Issue retry={reset}> -->
```

Effort: S.

### U3. Modal body chrome

**Context.** Eight modal bodies restyle their own `h2`, form column and footer, and they
already differ (1.05em against 1.1em, 1em against 0.6em margins): LinkForm, Reveal, AppForm,
KeyForm, WebhookForm, ProjectForm, TodoForm and Confirm. PR #48 shared the dialog behaviour
(`modal/dialog.ts`), but not this look.

**Options.**

1. Add a ui `Dialog` frame with `title` and an `actions` snippet. Modal bodies render inside
   it.
2. Leave the CSS in each body.
3. Use a shared global stylesheet. This breaks the scoped-CSS rule, so it is rejected.

**Recommendation.** Do 1. Do TodoForm last, after the todos workflow merges.

```svelte
<Dialog title="Add link">
	<form id={fid} …>…</form>
	{#snippet actions()}
		<Button variant="ghost" onclick={close}>Cancel</Button>
		<Button variant="primary" type="submit" form={fid}>Add</Button>
	{/snippet}
</Dialog>
```

Effort: M.

### U4. Who owns the delete confirm

**Context.** Delete confirmation is written six different ways. Some slices have a
`Delete.svelte` component that takes a snippet and wraps the whole `<li>`, and others call
`modal.confirm` inline. Failures are reported three different ways.

**Options.**

1. Use per-slice `Delete.svelte` components everywhere. That means five or more near-identical
   components.
2. One helper in `$lib/query` that confirms, runs the action and reports a failure in a toast.
3. Call `modal.confirm` inline in every row.

**Recommendation.** Do 2, and delete the per-slice `Delete.svelte` components. Do
`todos/components/Delete.svelte` after the todos workflow merges. The row's `Status` still
reads the mutation.

```ts
export const confirm = async (ask: Ask, run: () => Promise<unknown>) =>
  (await modal.confirm(ask)) && run().catch((err) => toast.error(message(err)));

// row
confirm({ title, action: "Delete", body: warn, verify: name }, () =>
  drop.mutateAsync({ path: { id } }),
);
```

Effort: S–M.

### U5. `Status` API and live regions

**Context.** The mapping from a mutation to a `Status` state is copied in six forms, and
some drop `saved` or merge two mutations. Every `Status` is also a `role="status"` live
region, so a list of 50 rows has 50 of them. They keep saying "Saved" after the dot fades.

**Options.**

1. Leave it as is.
2. Give `Status` a structural `of` prop (one mutation or an array). Remove `role="status"`
   from the dot and announce only failures, through one polite region mounted in `Modals`.

**Recommendation.** Do 2.

```ts
type Of = {
  isPending: boolean;
  isError: boolean;
  isSuccess: boolean;
  error?: { message?: string } | null;
};
let { state, of }: { state?: State; of?: Of | Of[] } = $props();
```

Effort: S.

### U6. Keyboard model for lists and overlays

**Context.** Menu, Command and Combobox each handle the keyboard differently. In Combobox,
Tab steps through every option, ArrowDown takes focus away from the search box, and the
search box isn't linked to its list. Combobox also predates `Popover`: its absolutely
positioned panel gets clipped by `overflow` ancestors, and it has its own outside-click
and Escape handling. List rows can only be reached with Tab.

**Options.**

1. **Make the overlays consistent, and add roving focus to `List.Root`.** Combobox renders
   through Popover and follows the Command model: focus stays in the search box and
   `aria-activedescendant` points at the active option. All three widgets share one
   `step()` helper. `List.Root` handles ↑/↓ and j/k to move, Enter to open, F2 to rename, `.`
   to open the menu, and Backspace to delete after a confirm. A `?` sheet lists the keys.
2. Make only the overlays consistent, and add `/` (search) and `C` (create) everywhere.
   Rows stay on Tab.

**Recommendation.** Do 1. Each part only needs to be built once now that `List` exists in
ui. That is what makes the app keyboard-first rather than just having a few hotkeys.

```ts
// packages/ui/src/lib/list.ts
export const step = (key: string, at: number, n: number) =>
  ({ ArrowDown: at + 1, ArrowUp: at - 1, Home: 0, End: n - 1 } as Record<string, number>)[key];
```

Effort: M for the overlays and M for the list keys.

**Options.**

### U9. Tailwind

**Context.** The app loads Tailwind, but no markup uses its utility classes. Its global
utilities can collide with scoped class names (`.grid` in 5 files). The ui pass did not
remove it, because the app quietly depends on Tailwind's reset (Preflight). That reset
covers heading and paragraph margins, button resets, `svg { display: block }` and list
resets. Tailwind v4's `preflight.css` calls `--theme()`, so it can't be imported without
the Tailwind compiler.

**Options.**

1. Keep Tailwind.
2. Copy the reset rules the app relies on into `routes/layout.css` (about 40 lines), then
   remove the plugin, the import and both dependencies.
3. Remove it outright and fix whatever breaks.

**Recommendation.** Do 2, with a before/after screenshot pass over the main routes. Update
`apps/dashboard/AGENTS.md`, which says "TypeScript, Tailwind, bun". Effort: M.

### U10. Mermaid and highlighter loading, and the static-imports rule

**Context.** Markdown imports `Fence` statically, and `Fence` statically imports `Mermaid`
(`beautiful-mermaid`) and `Code` (`@tanstack/highlight`). The root layout mounts the agent
dock, which renders `Markdown`. That puts both libraries in the root chunk of every page.
Measured from the installed packages (files gzipped, not a production build):

| Package                                  | Raw             | Gzip        |
| ---------------------------------------- | --------------- | ----------- |
| `beautiful-mermaid` 1.1.3                | 336 KB          | 68 KB       |
| `elkjs` (bundled, imported by it)        | 1.6 MB          | 466 KB      |
| `@tanstack/highlight` (all 54 languages) | 576 KB unpacked | about 14 KB |

Mermaid costs about 530 KB gzip, far above the "under 50 KB, leave it" threshold the audit
proposed. The highlighter is small. The house rule allows only static, top-level imports.

**Options.**

1. Keep static imports and pay about 530 KB gzip on every page.
2. Make one exception to the rule: `Fence` loads Mermaid in markup with
   `{#await import('./Mermaid.svelte') then m}<m.default {value} />{/await}`, showing `Code`
   while it loads. Every caller gets diagrams lazily.
3. Make Mermaid opt-in, with no exception. `Markdown` stops importing it, and callers that
   want diagrams pass a `fence` override (`components={{ fence: Diagram }}`). Todo
   descriptions and prototype pages pass it. The agent dock doesn't, so mermaid blocks in
   chat show as highlighted source.

**Recommendation.** Do 3, and keep the highlighter static. The rule stays absolute, the
root chunk loses the weight, and the cost moves to the routes that show diagrams. If chat
needs rendered diagrams later, choose 2 then, as a written exception limited to markup
`{#await import()}` inside ui renderers.

**Sketch.** Remove the `lang === 'mermaid'` branch from `markdown/Fence.svelte`, add a
`markdown/Diagram.svelte` (Mermaid with `Code` as the fallback) and export it, and give
`Markdown` a `components` prop. Effort: S.

## Lists and slices

### L1. Rename entry point and Inline's resting cue

**Context.** Renaming works differently in each slice. Some rows have an `Inline` that is
always on, and others put it behind a menu. On detail pages an `Inline` field looks like
static text until you hover it. On `/projects/[id]/settings`, "What is this for?" reads as
placeholder text, and the label appears twice (`Field label` and `Inline label`).

**Options.**

1. In rows, the name is always a link and Rename lives in the menu, where it opens `Inline`
   on demand. Detail headers keep an `Inline` that is always on, with a resting cue: a
   dotted underline or a faint pencil when focused.
2. An `Inline` that is always on everywhere, with a separate "open" icon in rows.

**Recommendation.** Do 1. Rows open things and headers edit them, so the whole row stays
clickable. Drop the duplicate label: `Field` labels the control. Effort: S–M.

### L2. Query-factory naming

**Context.** The same action has different names in different `api/*.query.ts` files
(`create` against `mint`, `remove` against `retire`).

**Options.**

1. CRUD verbs (`list`, `get`, `create`, `update`, `remove`), plus a domain verb only for
   actions that aren't CRUD (`rotate`, `test`).
2. Domain verbs everywhere.

**Recommendation.** Do 1. It matches the todos reference slice, and
`import * as Webhooks from '../api/webhooks.query'` reads as `Webhooks.create()`.
Effort: S.

### L3. Event timeline data path

**Context.** The project "Logs" timeline reads a remote function straight from markup and
never refreshes after a project write. People/Activity reads the same kind of data through
the SDK.

**Options.**

1. Use TanStack over the existing remote function, with key `["events", source, id]`. Project
   mutation factories invalidate it.
2. Add a public `/event` SDK route and use `getEventOptions`.
3. Keep the remote function and call `.refresh()` from project mutations.

**Recommendation.** Do 1. It follows the rule that internal data goes through remote
functions and TanStack, it adds no API, and one `Timeline` can then serve both people and
projects. Effort: S.

### L4. Where page data loads

**Context.** On the server render, most lists showed skeletons because the server and the
browser used different query keys. PR #49 fixed the keys (`queryClient(origin)`) and added
`warm()`. It then applied the fix to the project layout and the project overview, which
removed their layout shift. `/projects`, `/files`, `/developers/keys` and admin still render
skeletons first.

**Options.**

1. Load data only in the browser, and size the skeletons to match the real content.
2. Each list and detail route gets a `+page.ts` that warms its above-the-fold queries over
   `event.fetch`.
3. Move everything to remote functions awaited in markup.

**Recommendation.** Do 2, using the `warm()` helper from PR #49.

```ts
// routes/(app)/projects/+page.ts
export const load = async ({ parent }) => warm((await parent()).queryClient, Projects.list());
```

Note: `queryClient(origin)` assumes one origin per server process. With several origins,
the server render just misses the cache, so nothing breaks. Effort: M.

### L5. Admin information architecture

**Context.** Admin Overview and Database show the same facts band. The table row counts
always read "0 rows" (a separate bug). The instance has 11 tables.

**Options.**

1. Overview shows facts and recent logs; Database keeps the tables.
2. Merge them into one "Instance" page with the tables and the end of the log, and drop
   the Database nav item.

**Recommendation.** Do 2, and fix the row count while you're there. Effort: S.

### L6. How admin uses TanStack

**Context.** Admin pages call remote functions straight from markup and refresh them

## Product roadmap

### P1. EAP-style todos roadmap

**Context.** Todos already have most of what a work breakdown needs:

- `parentID` and a dense `position` (core refuses cycles)
- a free-text `stage`, with its date range taken from the todos in it (`Todo.stages`)
- planned dates (`startDate`, `dueDate`) and actual dates (`timeStarted`, `timeDone`)
- a timeline view that draws planned and actual bars

The table view builds the tree in the browser (`features/todos/tree.ts`) and already
supports indent and outdent (`moves()`). It only sees the page that loaded, though: at most
100 rows (`pageSize` max). So the `total`/`done` counts on a parent are wrong once a
project has more todos than that.

The steps below are in recommended order. Each one ships alone.

#### P1a. A tree read with roll-ups

1. Load every todo in a project in the browser (fetch all pages) and keep using `tree()`.
   It needs no core change, but the payload grows with the project and still caps out.
2. **A `Todo.tree` op in core**, using a recursive CTE scoped to a source. It returns nodes
   in tree order with depth and roll-ups: count, done, earliest start, latest due, and
   weighted progress once P1d lands.
3. A materialized path or closure table. Subtree reads get faster, but every move has to
   rewrite rows, and it needs a migration.

**Recommendation: 2.** It needs no migration and works on the existing `todo_parent` index.
It runs as one query, and the browser keeps `visible()` and `moves()`.

```sql
with recursive walk as (
  select t.*, 0 as depth, array[t.position] as path from todo t
  where t.source = $1 and t.source_id = $2 and t.parent_id is null and t.time_deleted is null
  union all
  select c.*, w.depth + 1, w.path || c.position from todo c
  join walk w on c.parent_id = w.id where c.time_deleted is null
)
select * from walk order by path;
```

Roll-ups are a single pass in TS, from the bottom of the tree up, over the ordered rows.
Expose it as `GET /todo/tree?source&sourceID`. Effort: M +gen.

#### P1b. Outline view

Add a fifth view, `outline`, next to table, board, timeline and list. It is an editor you
drive with the keyboard: Enter adds a sibling, Tab indents, Shift+Tab outdents, Alt+↑/↓
moves a row, and F2 renames. It reuses `moves()` and `Todo.move` and reads P1a's tree. Its
keys follow U6. **Recommendation:** build it after P1a and U6. Effort: M.

#### P1c. Dependencies and Gantt

1. **A `todo_link` table** (`from`, `to`, `type`), with finish-to-start only at first. Core
   refuses cycles, the same way it does for parents.
2. Keep dependencies in `metadata.links`. It needs no migration, but there is no integrity
   check, and they can't be queried or checked for cycles.
3. No dependencies. The "Gantt" is just the timeline with tree rows.

**Recommendation: 1, without auto-scheduling.** The Gantt is the existing timeline with
P1a's tree rows and dependency arrows. When a successor starts before its predecessor is
due, show a warning, but never move dates automatically. Effort: L +mig.

#### P1d. Weight and progress

1. Keep the count-based progress (`done/total`).
2. **Add a `weight` integer column** (default 1). Progress is derived: a leaf counts 1 when
   done and 0 otherwise, and a parent shows the weighted mean of its children.
3. A manual `progress` percentage on every todo. It drifts from status, and parents still
   need a rule.

**Recommendation: 2.** It is one column, and it fits P1a's roll-up pass. Effort: S +mig.

#### P1e. Parent dates

1. **Derive them when not set.** A parent with no dates of its own shows its children's
   span, marked "from sub-issues". A parent with its own dates keeps them, and a child that
   runs past them shows a warning.
2. Always derive them, and make parent dates read-only.
3. Enforce them: refuse a child whose dates fall outside its parent's.

**Recommendation: 1.** It comes from P1a's roll-ups for free and never blocks an edit.
Effort: S.

#### P1f. Baselines

1. **A `baseline` table** (`id`, `source`, `sourceID`, `name`, `time_created`, and a jsonb
   snapshot of `{ id, startDate, dueDate, weight }[]`). The timeline can draw one baseline
   as ghost bars.
2. Rebuild past plans from the event history. This needs every date change to be an event
   with old and new values, and it is slow to query.
3. Skip baselines.

**Recommendation: wait until P1c is in use, then choose 1.** A baseline only matters once
dates are planned against dependencies. Effort: M +mig.

### P2. GitHub token source for a future GitHub sync

**Context.** Some groundwork for a sync already exists:

- annotations under `github.com/` are reserved and read-only through the API
- a unique index on `metadata.annotations['github.com/issue-id']` stops an issue from being
  imported twice
- `Connection` (core `platform/connection`) stores a user's tokens for each provider, but
  nothing fills it yet

Login through GitHub goes through the shared OpenAuth issuer. That issuer only asks for
profile and email, and by design it never touches an app's database. So the login token
can't be reused for a sync.

**Options.**

1. **A GitHub App.** It mints short-lived installation tokens from the app's private key,
   gets issue webhooks out of the box, is installed per org or repo with fine-grained
   permissions, and writes as the app's bot. Each project stores its installation and repo
   as annotations (`github.com/installation`, `github.com/repo`).
2. **A "Connect GitHub" OAuth flow in the app.** It stores a user token in `Connection`.
   Writes appear as that user, but the sync stops when that user disconnects or leaves, and
   webhooks have to be set up per repo by hand.
3. **A personal access token** pasted into Settings and stored in `Connection`. It is the
   fastest to build, but the tokens last a long time and are tied to one person.
4. **Widen the issuer's login scopes to `repo`** and pass the token on. Every login then
   asks for repo access, and it breaks the issuer's "never touches the app" design.

**Recommendation: 1.** A sync belongs to a project rather than a person, it needs webhooks,
and installation tokens expire within an hour, so nothing long-lived is stored. Keep
`Connection` for later actions done as a specific user, such as commenting as yourself.
Skip 3 and 4.

**Sketch.** You set the env vars: `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY` and
`GITHUB_WEBHOOK_SECRET`. The rest:

- a `platform/github` module in core with `token(installation)`, cached until it expires
- a webhook route in functions that verifies the signature and enqueues a job
- a queue job that upserts todos by `github.com/issue-id`

Effort: L.
